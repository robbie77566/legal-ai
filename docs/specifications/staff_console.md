## 1. Roles

| Role | Who | Lands on | Sees in the `/ops` nav |
|---|---|---|---|
| `ADMIN` | founder / ops | `/ops` | Overview · Holds · Cases · Organisations · Verifications · Quotes · Record Desk · Accounts · Promos · Money · Feedback · Retention · Flags · Team |
| `SUPPORT` | customer-facing staff (new) | `/ops` | Overview · Cases · Organisations · Verifications · Quotes · Record Desk · Accounts · Feedback (the four professional pages read-only; the Record Desk lets Support move a request along, §12) |
| `ATTORNEY` | quality reviewer | `/qa` | (no `/ops` access) |
| `CLIENT` | the family | `/cases` | never reaches `/ops` |

Admin is a superset of Support by construction. The web nav is UX gating only (`apps/web/app/ops/layout.tsx`, `apps/web/middleware.ts`); the API hook in `apps/api/src/routes/ops.ts` is the real gate:

- `ADMIN`: everything under `/ops`.
- `SUPPORT`: every `GET` except `/ops/payments*`, `/ops/refunds`, `/ops/invoices*`, `/ops/credits*`, `/ops/promos`, `/ops/retention-candidates`, `/ops/sentry-test`, `…/cogs`; exactly these `POST`s on a case: `delay-ours`, `delay-cleared`, `resume`, `contact`, `requests`; and `PATCH /ops/investigations/:id` limited in-route to `IN_PROGRESS` / `DELIVERED`. Everything else is 403 with a sentence saying who can.

## 3. Money and refunds (OPS-2)

- `Refund` table: one row per refund actually issued (partial refunds stack); `Payment` gains `paymentIntentId`, `chargeId`, `refundedCents`, `refundedAt`, `disputedAt`, `disputeStatus`, status `PARTIALLY_REFUNDED`. Migration `20260907000016_refund_ledger`.
- `apps/api/src/services/refunds.service.ts` — `issueRefund` (Stripe with an idempotency key → one tenant transaction: Refund row, rollup + status, `payment.refunded` v2 event, `REFUND` audit row); over-refund / free-purchase / open-dispute walls; webhook handlers match `charge.refunded` and `charge.dispute.*` by payment intent (the old matcher compared a payment-intent id to a checkout-session id and updated nothing in production).
- Routes: `GET /ops/payments`, `GET /ops/payments/summary?days=`, `GET /ops/refunds`, `POST /ops/payments/:id/refund`; `POST /ops/cases/:id/refund` kept as a wrapper.
- Numbers: **collected** = charges on payments created in the period; **refunded** = refunds on those *same* payments whenever issued (cohort); **refund rate** = refunded ÷ collected; **net** is before Stripe fees (not synced).

## 4. Case file and Support (OPS-6)

- `apps/api/src/services/case-file.service.ts` — `getCaseFile` (owner connection; staff hold no `CaseAccess`), `staffDocumentDownloadUrl` (same 5-minute presign as the customer route, never for quarantined files), `staffReportPdf` (re-renders any released version with FR-7 re-verification). Downloads are audited under the staff member.
- **Contact log**: `SupportNote` rows (channel, body, author) + a `support.contacted` event carrying only `{noteId, channel}` — free text never enters the PII-minimal event stream. `POST /ops/cases/:id/contact`.
- Migration `20260907000017_support_role` adds the enum value.

## 5. Requests to an Admin

- `StaffRequest` (`REFUND` | `CASE_DELETE` | `ACCOUNT_DELETE`; reason from a fixed list; optional note and partial amount). One *open* request per case + type (partial unique index). Migration `20260908000018_support_notes_requests`.
- `apps/api/src/services/staff-requests.service.ts`: `openRequest` (refuses refund requests with no refundable payment; emails every Admin once), `listRequests` (Support sees only their own), `decideRequest` (approve runs `issueRefund` / `deleteCaseScoped` / `deleteAccount` under the **Admin's** id; decline requires a note; both write `request.decided` + audit).
- Routes: `POST /ops/cases/:id/requests` (Support/Admin), `GET /ops/requests`, `POST /ops/requests/:id/decide` (Admin only — the hook keeps Support off it).
- Surfaces: case file (both roles; Admin decides inline), Overview (Admin: Approval cards; Support: Waiting on an admin), Money → Needs a decision.

## 6. Invites (auth design §4.6)

- `POST /permissions/users` now issues a hashed 24-hour `inviteToken` and sends `sendInvite` (who added you, as what, the two steps, what you will see). Returns `invite.setupUrl` **only when the email could not be delivered** so the admin can hand it over.
- `POST /permissions/users/:id/invite` resends (rotates the token); 409 once a password exists (use Forgot password).
- `POST /auth/setup` (public prefix, token-verified, rate-limited) sets the first password; single-use. The web page `/auth/setup-password` then sends the person to `/auth/signin?welcome=1&email=…`.
- `GET /permissions/users` exposes `active`, `invitePending`, `inviteExpired` for the team list.

## 10. Feature flags (workstream J, 2026-10-19)

Every professional surface ships dark behind a `FeatureFlag` row with per-organisation overrides (`persona_rollout_plan.md` §7 "Flags, not branches" and the test-in-production protocol). A flip is a row update, never a deploy: **a flip is live within 15 seconds on every instance** — reads come from a per-process cache with a 15 s TTL (`packages/database/flags.ts`), and the writing instance drops its own cache at once. Overrides are keyed by `tenantId` (what RLS scopes on) until the `Organisation` model (1:1 with `Tenant`) lands; the override list then reads the same.

- Tables: `FeatureFlag` (`key`, `enabled`, `description`, `updatedBy`, `updatedAt`) and `FeatureFlagOverride` (`flagKey`, `tenantId`, `enabled`, `note`, `updatedBy`, `updatedAt`; unique per flag + tenant). System tables: no RLS, owner connection only. Migration `20261019000030_feature_flags` seeds the six keys, all off.
- The six keys: `counsel_surfaces` (counsel web surfaces), `counsel_checkout` (ladder, packs, first-free review), `offices` (PD office organisations, allowances, ACH), `record_desk` (verification view and exports), `clinic_inbox` (consented-packet inbox, public-interest allowance), `long_records` (2,000-page split and merge). Unknown keys are refused by the typed guard (`FlagKey`) and answer 400 on the API.
- Precedence: a tenant override wins over the global value; no override → global; a key missing from the table → off.
- Library (`packages/database/flags.ts`): `isFlagOn(key, tenantId?)`, `listFlags(tenantId?)` → `{ key, enabled, effective, overridden }[]`, `setFlag`, `setOverride`, `clearOverride` (each returns `{ key, tenantId, before, after }` for the audit row), `listFlagsForAdmin()`, `__invalidateFlagCache()`.
- Routes: `GET /flags` (any signed-in caller; the effective map for the caller's tenant, `{ counsel_surfaces: false, … }`); `GET /ops/flags` (Admin, Support); `PUT /ops/flags/:key` `{ enabled }`, `PUT /ops/flags/:key/overrides/:tenantId` `{ enabled, note? }`, `DELETE /ops/flags/:key/overrides/:tenantId` (Admin only — Support's writes get the usual 403 sentence from the ops hook). Every write is one `FLAG_CHANGE` audit row with `key`, `scope`, `tenantId`, `before`, `after` (and the note), under `caseId = flag:<key>`.
- Guarding a surface: `preHandler: requireFlag('counsel_surfaces')` (`apps/api/src/plugins/flags.ts`) answers **404 `{ error: 'Not available' }`** when the flag is off for `request.auth.tenantId` — 404, not 403, so a dark surface does not confirm it exists. The web reads flags with `getFlags()` (server, forwards the session cookie) or `useFlags()` (client) from `apps/web/lib/flags.ts`; both default to all-dark when the API cannot be reached. The API guard is the real gate.
- Page: `/ops/flags` — the six flags, global toggle (Admin), override list per flag with tenant id + note, add/remove (Admin); Support sees it read-only. In the nav for Admin only.
- Rollout order per surface (plan §7): migrate and deploy dark → override on for the founder's test organisation → override on for the first external organisation → global on at the phase gate. Rollback of a surface is the same flip in reverse.
- Tests: `apps/api/tests/flags.integration.test.ts` (flip without deploy incl. the TTL, precedence, roles, audit), `packages/database/tests/flags.integration.test.ts` (guard, precedence, cache), web `FlagsPage` and the role-filtered nav in `OpsDashboard`.


## 11. Organisations and account kinds (added 2026-10-19)

The identity **expand** step of the persona rollout (`docs/implementation/persona_rollout_plan.md` §5 A, §7 "Deploy discipline"). Migration `20261019000029_organisations`; everything is additive and the `Role` column and every gate that reads it keep working unchanged.

**The model.**

| Table / column | What it is |
|---|---|
| `User.accountKind` — `FAMILY` \| `PROFESSIONAL` \| `STAFF` (default `FAMILY`) | *Who* a person is: which surface they belong to. Backfilled by the migration: `CLIENT` → `FAMILY`; `ADMIN`, `SUPPORT`, `ATTORNEY`, `INVESTIGATOR`, `VIEWER` → `STAFF` (every non-CLIENT role is staff per §1). |
| `StaffGrant { userId, kind: ADMIN \| SUPPORT \| REVIEWER, grantedBy, grantedAt, revokedAt? }`, unique per user + kind | *What a staff member may do*, as a set. Backfilled `ADMIN`→`ADMIN`, `SUPPORT`→`SUPPORT`, `ATTORNEY`→`REVIEWER`; `INVESTIGATOR`/`VIEWER` get no grant (no console surface). Revocation is a timestamp, never a delete. `POST /permissions/users` creates the matching grant; `PATCH /permissions/users/:id` revokes the old one and grants the new. |
| `Organisation { tenantId @unique, kind: FIRM \| PD_OFFICE \| CLINIC \| FAMILY, name, legalName?, billingEmail?, pilot, pilotEndsAt?, allowanceRecords, allowanceResetsAt?, features, isTest }` | The 1:1 profile of a Tenant, so RLS stays tenant-scoped and every existing tenant table is already the organisation's data. Pilot flag, allowance and `features` are read by the price book (B) and flags (J); `isTest` organisations are excluded from Money and analytics. Family tenants have no row yet (nothing reads one). |
| `Membership { organisationId, tenantId, userId, role: OWNER \| ATTORNEY \| INVESTIGATOR \| VIEWER, invitedBy? }`, unique per organisation + user | A person's seat. `tenantId` is denormalised so the RLS policy is the same plain column test as the other tenant tables. |
| `User.barNumber?, barState? ('TX'), barVerifiedAt?, barVerifiedBy?, practiceType?` (`writ`, `appellate`, `trial`, `pd`, `clinic`, `investigator`, `other`) | The professional profile. The bar number is stored **unverified** at sign-up; the staff verification queue is workstream G. |

RLS: `Organisation` and `Membership` carry `tenant_isolation_policy_*` (USING + WITH CHECK on `tenantId`), ENABLE without FORCE like every other table since `20260901000012`. `StaffGrant` is a system table read on the owner connection. Proven by `packages/database/tests/organisations-rls.integration.test.ts`.

**Professional accounts keep `role: CLIENT`.** Every existing staff gate (`/ops`, `/qa`, `/admin`, `/dashboard`, `/workspace`) refuses `CLIENT`, so a professional can never reach a staff surface through the legacy column; `Role.ATTORNEY` stays what §1 says it is, the staff reviewer. The api auth plugin additionally refuses a `PROFESSIONAL` on `/ops`, `/qa`, `/admin` and `/permissions` whatever the role column says, and the web middleware does the same for `/ops`, `/qa`, `/dashboard`, `/workspace` (`apps/web/lib/route-access.ts`).

**Reading the two shapes at once.** `packages/database/staff.ts`:
- `effectiveAccountKind(user)` — the stored kind, except a row still at the `FAMILY` default with a staff role counts as `STAFF` (a staff account created by a pre-expand code path, the same answer the backfill gives).
- `effectiveStaffGrants(user)` — the active grant rows when the person has any rows (revoked ones included), else the one grant the role implies. A non-STAFF account never holds a grant.
- `hasGrant(grants, kind)` — ADMIN is a superset of SUPPORT by construction.

**Per request, from the database.** The api auth plugin (`apps/api/src/plugins/auth.ts`) puts `accountKind` and `grants` on `request.auth` from the database on every request (the session token format is unchanged); `requireAccountKind(...)` and `requireGrant(...)` in `apps/api/src/plugins/guards.ts` read them. `/counsel/*` uses `requireAccountKind('PROFESSIONAL')` plus a per-request membership load, so a removed seat or a revoked grant is a 403 on the very next call, not the next sign-in. The web session carries `accountKind` beside `role` (refreshed from the database on every JWT refresh); `/go` lands a professional on `/counsel` (`apps/web/lib/landing.ts`).

**Routes.** `POST /counsel/signup` (public, rate-limited, bcrypt cost 12, enumeration-safe like `/buy/account`: a duplicate email answers `{ ok: true }` with no ids): creates Tenant + Organisation + User (`PROFESSIONAL`, role `CLIENT`) + `OWNER` membership in one transaction and writes an `ACCOUNT_SIGNUP` audit row (never the bar number). `GET /counsel/me`: the user, their organisation (kind, name, pilot, allowance), their membership role, bar fields and `barVerified`.

**Record inventory (workstream D, 2026-10-19, January slice).** Migration `20261019000032_record_inventory`, additive. `Document.volumeKind` (`REPORTER | CLERK | EXHIBIT | UNKNOWN`, default `UNKNOWN`), `volumeLabel` ("RR vol. 3 of 7"), `volumeIndex`, `volumeCount`, `volumeConfirmed`, `ocrConfidence` (mean over its pages once digitised); `Case.recordBucket` (`SHORT | STANDARD | EXTENDED | LONG`), `Case.meteredPages` (`{ reporter, clerk, exhibit, unknown }`, billable pages per kind), `Case.inventoryAt`. The projection is written only by `recomputeMeter` (`apps/api/src/services/inventory.service.ts`) after every upload complete, ZIP entry batch, document removal, volume change and finished digitisation; the bucket comes from `classifyRecord` in `packages/case-lifecycle/pricing/buckets.ts` — reporter's-record pages alone; clerk's and exhibits metered separately; unlabelled pages counted under `unknown` and never in the bucket. Both tables already carry the tenant isolation policy, so the columns inherit RLS (`apps/api/tests/inventory.integration.test.ts` D6: another tenant's `GET /cases/:id/inventory` is 404).

Routes (family, case-member gate like `/cases/:id/pages`; counsel pages reuse them):
- `POST /upload/complete` — optional `volume: { kind, index?, count? }` from the uploader (stored confirmed); absent, the filename heuristic's suggestion is stored unconfirmed. Answers `{ documentId, volume }`.
- `GET /cases/:id/inventory` → `{ volumes: [{ kind, docs: [{ id, filename, label, index, count, pages, duplicatesIgnored, digitised, ocrConfidence, confirmed }], pages, ocrConfidence }], missing: [{ kind, index, count, label }], unknownCount, meteredPages: { reporter, clerk, exhibit, unknown, total }, bucket, bucketNote }`. A case RLS hides is 404; a same-tenant account without case access is 403.
- `PATCH /cases/:id/documents/:docId/volume` `{ kind, index?, count?, confirmed }` → `{ ok, document, inventory }`; appends `doc.volume_set` (kind and position only, never the filename); 400 on an index above the count.
- Read-only additions: `recordBucket`, `meteredPages`, `inventoryAt` on `GET /cases/:id` and on the ops case file (`case-file.service.ts`), whose documents also carry `volumeKind`, `volumeLabel`, `volumeConfirmed`. The family overage gate in `records-complete` still reads total billable pages, unchanged.

**Matters (workstream C, migration `20261019000031_matters`).** A professional opens a *matter* instead of taking the family quiz (`persona_rollout_plan.md` §3 writ practitioner / PD appellate attorney, §5 C). A matter is the counsel-facing shape of a Case, 1:1 through `Matter.caseId`: the vehicle chosen up front (`direct_appeal`, `pdr_clock`, `11.07`, `11.072`, `11.09`, `2254` — `CounselVehicle` in `packages/case-lifecycle/trap/vehicles.ts`; `11.071` and `capital: true` are refused with 422 `CAPITAL_REFUSED` by `vehicleAcceptance`), the optional lane, county, court, cause number, **client initials only** (one to four letters; no client name is accepted, stored, logged or audited anywhere), offence, sentence, the four dates (judgment signed, sentence imposed, notice of appeal filed, record filed), the prior-writ count and subsequent-writ flag, an outside-record note. Opening a matter creates the Case (`title = "<initials> — <vehicle label>"`, `Case.vehicle` set, status `AWAITING_DOCS`, `CaseAccess` for the opener), seeds `Case.facts` / `Case.deadlineFacts` / `convictionYear` the way the interview does (so the FR-5 deadline engine and the report read them unchanged) and the checklist (the form *is* the interview: `interview.completed` is emitted), appends `case.created` v2 (`vehicle`, `matterId`), sets `SUBSEQUENT_WRIT_MODE` when a prior writ is declared, and writes a `MATTER_OPENED` audit row (ids and vehicle only). The analysis run of a matter weights its screens by the vehicle: `planScreens(lane, vehicle)` in `apps/api/src/services/analysis.service.ts` reorders the lane's screens by `VEHICLES[vehicle].weightedScreens` (never dropping one) and records `vehicle` + `screenWeights` on `AnalysisRun.modelConfig`; a case with no matter row gets exactly today's plan and modelConfig. The TRAP clock (`computeTrapClock`) reads the matter's own date columns live. `Matter` carries `tenant_isolation_policy_matter` (USING + WITH CHECK on `tenantId`), proven by `packages/database/tests/matters-rls.integration.test.ts`; every route below is additionally scoped to the caller's organisation, so another organisation's professional gets a 404. The zod schemas and the response types live in `packages/case-lifecycle/matters.ts` and are shared with the web client (`createMatter`, `listMatters`, `getMatter`, `updateMatter` in `apps/web/lib/api.ts`); the pages are workstream F. No new environment variables.

**Clinics, offices, investigation layer (workstream I, 2026-10-19, January slice).** Migration `20261019000034_org_inbox`, additive. `Organisation.publicInterest` (default false) and `Organisation.securityContact`; `ConsentGrant.recipientOrganisationId` (the clinic the family named; null keeps the class-wide shape); three new tenant tables with the usual `tenant_isolation_policy_*` (proven by `packages/database/tests/org-inbox-rls.integration.test.ts`): `Invitation { organisationId, email, role, tokenHash (sha256, the raw token travels in the email alone), invitedBy, expiresAt, acceptedAt? }`, `PacketDelivery { tenantId = the CLINIC's tenant, organisationId, sourceTenantId, caseId, reportId, consentGrantId, deliveredAt, openedAt?, openedBy? }` (unique per clinic + report), `InvestigationRequest { organisationId, caseId?, requestedBy, kind CHRONOLOGY | RECORDS_TRACKER | OTHER, pages?, dueBy?, note, status OPEN | IN_PROGRESS | DELIVERED | DECLINED, assignedTo?, staffNote?, deliveredAt? }`. ## 12. Professional-era staff jobs (workstream G, 2026-10-19)

The January slice of persona_rollout_plan.md §5 G: the console gains the jobs the professional personas create for staff (plan §3 "Staff"). No schema change and no new environment variable; every route sits inside the `/ops` hook (§1) and every write is one audit row through `AuditService`. Routes in `apps/api/src/routes/ops-professional.ts` unless named otherwise; pages under `apps/web/app/ops/*`; typed helpers in `apps/web/lib/api.ts`.

**Bar verification — a human act.** `User.barNumber` is stored unverified at sign-up (§11). A staff member looks the number up in the State Bar of Texas directory *themselves*, checks the name, and presses one of two buttons. Nothing in the product calls the State Bar, and nothing ever will without a policy decision: the directory's terms, and the attorney's expectation that we do not scrape their licence, both say so. Audit action `BAR_VERIFICATION`, under `caseId = verification:<userId>` and the attorney's tenant; **the bar number never enters an audit row or an email.**
- `GET /ops/verifications` → `{ verifications: [{ id, name, email, barNumber, barState, practiceType, signedUpAt, organisation: { id, name, kind, isTest } | null, seat }] }` — `PROFESSIONAL` accounts with a bar number, `barVerifiedAt` null, not deleted, and not yet rejected. Support may read.
- `POST /ops/verifications/:userId/verify` (Admin) — sets `barVerifiedAt` / `barVerifiedBy`; audit `{ op: 'verified', before: { barVerifiedAt: null }, after: { barVerifiedAt, barVerifiedBy } }`; sends `sendBarVerified` ("your bar number is verified — your first review is free", with the link to `/counsel`). Already verified → 409; not a professional with a bar number → 404. Answers `{ ok, userId, barVerifiedAt, barVerifiedBy, emailed }`.
- `POST /ops/verifications/:userId/reject` `{ note }` (Admin; the note is required) — **keeps the account and clears nothing**: the decision and its reason live only in the audit row `{ op: 'rejected', note }`, which is internal and is never shown to the attorney. Sends `sendBarNotVerified`, a neutral "we could not verify" with no reason and no number, and a way to reply. After either decision the queue no longer lists the person (the rejected set is read back from the audit rows, so a reject is reversible by verifying later).
